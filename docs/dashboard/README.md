# CWIZ Enterprise 운영현황 대시보드 인수인계 가이드

> 다른 담당자 또는 AI가 기존 정책과 기능을 유지하면서 대시보드를 수정할 수 있도록 만든 기준 문서입니다.

- 최종 갱신일: 2026-08-27
- 운영 파일: `docs/dashboard/index.html`
- 공개 주소: <https://hikary83.github.io/kic-worktools/dashboard/>
- 관련 Jira: `CW2R-73` — `[CWIZ Enterprise] Admin 대시보드 및 통계 기능 단계별 구축`
- 현재 화면 구성: 공통 기간 조회 + 4개 탭 + 고객 활동·보안 접속 로그

## 1. 목적과 범위

CWIZ Enterprise Admin에 정식 대시보드·통계 기능이 개발되기 전까지 사용하는 임시 운영 보고 화면이다. 매주 CWIZ Enterprise에서 내려받은 Excel 파일을 사용해 다음 흐름을 한 화면에서 확인한다.

`이용신청 → 승인 → 고객사 등록 → 계측기 등록 → CMS 매핑 → 고객 사용 활동·접속 현황`

현재 범위에는 견적, 교정의뢰, 접수, 진행, 완료, 매출 통계를 포함하지 않는다. 원본 Excel에 없는 데이터는 추정하거나 만들어내지 않는다.

## 2. 운영 및 기술 원칙

1. 대시보드 수치는 업로드한 Excel 데이터에서만 계산하며 숫자를 하드코딩하지 않는다.
2. 원본 Excel은 읽기만 하며 수정하지 않는다.
3. 파일은 브라우저 메모리에서 처리한다. 별도 서버나 API로 Excel 내용을 전송하지 않는다.
4. 새로고침하면 선택한 파일과 계산 결과는 초기화된다. 브라우저 저장소에 데이터를 보관하지 않는다.
5. 외부 JavaScript 라이브러리나 CDN 없이 단일 HTML 파일로 동작한다.
6. 최신 Chrome 또는 Edge 사용을 기준으로 한다.
7. 현재 지원 확장자는 `.xlsx`뿐이다. `.xls`와 `.xlsm`은 지원하지 않는다.
8. UI는 PC 보고용이며 1440px 이상에서 보기 좋도록 구성한다.
9. 기존 기능을 수정할 때 다른 KPI·차트·표의 집계 정책을 임의로 바꾸지 않는다.
10. 아이디와 접속 IP는 화면에서 일부 마스킹하고, 원본 Excel 값은 변경하지 않는다.
11. 사용자가 집계 기준을 외우지 않아도 되도록 지표 옆 `i` 버튼과 상단 `통계 기준` 모달을 유지한다.

## 3. 파일 위치와 구조

```text
D:\Google Antigravity\kic-worktools
└─ docs
   └─ dashboard
      ├─ index.html          # 실행 파일: HTML, CSS, Excel 파서, 집계, 화면 렌더링, data/ 자동로드 포함
      ├─ README.md           # 이 문서
      └─ data/               # 주간 엑셀 5개 보관 폴더 (직원 접속 시 자동 로드용)
         ├─ manifest.json    # 파일명 매핑 설정
         ├─ 이용신청.xlsx
         ├─ 고객사현황.xlsx
         ├─ 고객사계측기현황.xlsx
         ├─ 데이터변경이력.xlsx
         └─ 보안접속이력.xlsx
```

`index.html` 실행 시 `data/` 폴더의 엑셀 5개를 자동으로 읽어와 바로 화면을 렌더링합니다. 수동 업로드 패널도 유지되어 필요 시 임시 엑셀을 즉석에서 검증할 수 있습니다.

## 4. 매주 사용하는 입력 파일

동일 기준일의 다음 5개 파일이 모두 필요하다.

| 역할 | 파일명 예시 | 화면 역할 |
|---|---|---|
| 이용신청 | `이용신청_2026-08-27.xlsx` | 신청·승인·대기·반려 및 신청 업체 내역 |
| 고객사현황 | `고객사현황_2026-08-27.xlsx` | 등록 고객사, 상태, 담당자 |
| 고객사계측기현황 | `고객사계측기현황_2026-08-27.xlsx` | 자산, CMS 매핑, 차기교정 현황 |
| 데이터변경이력 | `데이터변경이력_2026-08-27.xlsx` | 고객사의 실제 CWIZ 데이터 작업 로그 |
| 보안접속이력 | `보안접속이력_2026-08-27.xlsx` | 로그인 성공·실패, 접속 고객사·사용자, 반복 실패 확인 |

파일명에서 `YYYY-MM-DD` 형태의 날짜를 찾아 기준일로 사용한다. 다섯 파일의 기준일이 다르면 적용하지 않고 오류를 표시한다.

### 필수 컬럼

| 파일 | 필수 컬럼 |
|---|---|
| 이용신청 | 신청일자, 상태, 회사명, 사업자등록번호, 승인일자, 회사코드 |
| 고객사현황 | 회사코드, 회사명, 사업자번호, 보유자산, 상태, 영업 담당자, 등록일 |
| 고객사계측기현황 | 회사명, 사업자번호, 총자산, 미매핑, 교정 준비, 교정 임박, 기한 초과, 상태 |
| 데이터변경이력 | 일시, 고객사, 사용자, 아이디, 메뉴, 로그 유형, 대상, 변경 항목, 변경 전, 변경 후 |
| 보안접속이력 | 일시, 고객사, 사용자, 아이디, 로그 유형, 결과, 접속 IP |

다음 컬럼명은 같은 의미로 허용한다.

- `사업자번호` ↔ `사업자등록번호`
- `영업 담당자` ↔ `영업담당자`
- `교정 준비` ↔ `교정준비`
- `교정 임박` ↔ `교정임박`
- `기한 초과` ↔ `기한초과`
- `로그 유형` ↔ `로그유형`
- `변경 항목` ↔ `변경항목`
- `변경 전` ↔ `변경전`
- `변경 후` ↔ `변경후`
- `접속 IP` ↔ `접속IP`

컬럼을 찾을 때 제목의 공백, `*`, BOM 문자는 무시한다. 원본 데이터 값 자체는 변경하지 않는다. 시트별 상단 10개 행 안에서 필수 컬럼이 가장 많이 일치하는 행을 헤더로 선택한다.

## 5. 핵심 집계 정책

### 이용신청과 승인

- 이용신청: 이용신청 파일의 데이터 행 전체 수
- 승인·대기·반려: `상태` 값이 각각 정확히 일치하는 행 수
- 승인 고객사 KPI: 승인 행의 고유 사업자등록번호 수
- 사업자등록번호가 비어 있으면 회사명을 중복 판정의 대체 키로 사용
- 이용신청 카드의 승인 수는 승인 신청 건수이며, 승인 고객사 카드는 고유 고객사 수이므로 데이터에 따라 서로 다를 수 있음

### 등록 고객사

- 등록 고객사: 고객사현황 파일의 데이터 행 전체 수
- 정상·비활성: `상태` 값이 각각 정확히 일치하는 행 수

### 계측기와 CMS 매핑

- 등록 계측기: 고객사계측기현황의 `총자산` 합계
- 미매핑 계측기: `미매핑` 합계
- 매핑 완료: `총자산 - 미매핑`
- 매핑률: `(총자산 - 미매핑) ÷ 총자산 × 100`
- 총자산이 0이면 매핑률 계산 오류가 발생하지 않도록 0으로 처리
- 고객사 운영현황은 기본적으로 총자산 내림차순 TOP 10
- 미매핑, 교정 임박, 기한 초과 기준으로 정렬을 바꿀 수 있음

### 차기교정 관리

- 교정 준비·교정 임박·기한 초과는 원본 파일의 같은 이름 컬럼을 각각 합산
- 대시보드에서 날짜를 다시 계산하거나 상태를 재분류하지 않음

### 담당자 운영현황

- 고객사현황의 `영업 담당자`를 기준으로 집계
- 고객사현황과 고객사계측기현황은 숫자 이외 문자를 제거한 사업자등록번호로 연결
- 사업자등록번호가 일치하지 않으면 해당 고객사의 계측기 수치는 담당자 합계에 포함되지 않음
- 원본에 담당지사 컬럼이 없으므로 지사 집계는 하지 않음

## 6. 공통 기간과 Snapshot 정책

Excel 적용 후 화면 상단의 시작일·종료일을 바꾸고 `조회`하면 모든 **기간 기반 지표**가 같은 기간으로 갱신된다. 종료일은 파일명 기준일을 넘길 수 없다. 시작일이 종료일보다 늦으면 적용하지 않고 오류를 표시한다.

빠른 기간은 다음과 같다.

- 이번 주: 기준일이 속한 주의 월요일~기준일
- 최근 7일: 기준일 포함 최근 7일
- 이번 달: 기준일이 속한 달의 1일~기준일
- 파일 전체: 다섯 파일의 날짜형 데이터 중 가장 이른 날짜~기준일

예: 기준일이 `2026-08-27`이면 이번 주는 `2026-08-24~2026-08-27`이다. 기본값은 이번 주다.

기간 기반 지표와 Snapshot 지표를 혼동하지 않는다.

- 기간 적용: 이용신청, 기간 승인 고객사, 신규 등록 고객사, 고객 데이터 작업, 로그인 성공·실패, 접속 고객사·사용자
- 기준일 현재: 등록 고객사, 등록 계측기, 미매핑, 매핑률, 차기교정, 전체 미처리 대기
- 각 카드·패널의 배지에 `기간 적용` 또는 `기준일 현재`를 표시한다.

### 이용신청 처리 현황

- 선택 기간: 신청일자가 시작일~종료일에 포함된 신청만 집계
- 이월 대기: 시작일보다 이전에 신청됐고 현재 상태가 `대기`인 건
- 전체 미처리: 이용신청 파일 전체에서 현재 상태가 `대기`인 건

### 고객 사용 활동

- 선택 기간: 로그 `일시`의 날짜가 시작일~종료일에 포함된 행
- 활동 고객사: 선택 기간의 고유 고객사 수
- 활동 사용자: `고객사 + 아이디` 조합의 고유 수. 아이디가 없으면 사용자명을 사용
- 작업 로그: 선택 기간의 로그 행 전체 수
- 활동 고객사 TOP 5: 작업 로그 수 내림차순, 동률이면 최근 활동 순
- 최근 활동: 선택 기간의 일시 내림차순 최근 8건

### 신규 고객사와 접속 현황

- 신규 등록 고객사: 고객사현황의 `등록일`이 선택 기간에 포함된 행 수
- 로그인 시도: 보안접속이력에서 `로그 유형=로그인`인 행 수
- 로그인 성공·실패: 로그인 행 중 `결과` 값이 각각 `성공`, `실패`인 행 수
- 접속 고객사: 로그인 성공 행의 고유 고객사 수
- 접속 사용자: 로그인 성공 행의 `고객사 + 아이디` 고유 수. 아이디가 없으면 사용자명을 사용
- 반복 실패 ID·IP: 선택 기간의 로그인 실패가 5회 이상인 고유 ID·IP 수
- 고객 이용 탭의 고객사 TOP 5는 로그인 성공 수 내림차순으로 표시
- 보안 접속 탭의 최근 실패는 일시 내림차순 최근 8건으로 표시
- 기간에 따라 파일별 데이터 시작일이 다를 수 있으므로, 값이 0이라고 해서 반드시 사용이 없었다고 단정하지 않는다.

현재 버전은 현재 상태를 보여주는 Snapshot 중심이다. 전주 대비 증감은 이전 주 파일을 함께 입력받는 기능이 추가되기 전까지 계산하지 않는다.

## 7. 고객 활동 로그 분류 정책

분류는 아래 우선순서로 적용한다.

1. `변경 항목`이 `첨부 추가`이면 **첨부 추가**
2. `메뉴=사용자 관리`이고 `로그 유형=등록`이면 **사용자 등록**
3. `메뉴=계측기 통합 대장`, `로그 유형=등록`, `변경 후=계측기 등록`이면 **계측기 등록**
4. `로그 유형=수정`이면 **정보 수정**
5. 위 조건에 해당하지 않으면 원본의 로그 유형을 사용하고, 로그 유형도 없으면 **기타**

작업 유형 막대는 현재 네 유형(계측기 등록, 정보 수정, 첨부 추가, 사용자 등록)을 표시한다. 새로운 유형은 작업 로그 전체 수와 최근 활동 표에는 포함되지만, 막대에 표시하려면 `renderActivitySection()`의 유형 목록과 HTML 막대를 함께 추가해야 한다.

## 8. 화면 구성

화면 순서는 다음과 같다.

1. 기준일·최근 적용 시간·보고 모드·인쇄
2. Excel 5개 선택 및 데이터 적용
3. 공통 시작일·종료일·조회와 빠른 기간
4. 4개 탭: 운영 요약 / 신청·고객사 / 고객 이용 / 보안 접속
5. 상단 KPI와 기간·Snapshot 배지
6. 탭별 차트·요약·표
7. 상단 `통계 기준` 버튼 및 지표별 `i` 설명

탭별 역할은 다음과 같다.

- 운영 요약: KPI, 이용신청 처리, CMS 매핑, 차기교정, 기간 접속·활동 요약
- 신청·고객사: 기간 신청·승인·신규 등록·현재 대기, 신청 업체, 고객사 TOP 10, 담당자 현황
- 고객 이용: 접속 고객사·사용자·성공 로그인·데이터 작업, 일별 접속, 접속 고객사 TOP 5, 데이터 작업 유형·최근 활동
- 보안 접속: 로그인 시도·실패·반복 실패 ID·IP, 일별 성공·실패, 반복 실패 목록, 최근 실패 10건

아이디는 일부만 남기고 마스킹하며, IPv4 주소는 뒤 두 옥텟을 `***`로 표시한다. 반복 실패 기준은 동일 ID 또는 IP의 실패가 선택 기간에 5회 이상인 경우다.

`통계 기준` 모달은 현재 선택 기간, Snapshot 기준일, 지표별 정의와 원본 컬럼을 표시한다. 지표 옆 `i`에 마우스를 올리면 짧은 설명을, 누르면 같은 기준 모달의 해당 항목을 연다.

보고 모드는 파일 업로드 영역과 성공 안내 등을 숨겨 캡처·인쇄에 적합한 화면으로 바꾼다.

## 14. ⚠️ 현재 알려진 이슈 및 주의사항 (새로고침 시 데이터 유지 관련)

> **[현상 요약]**  
> 웹 화면에서 엑셀 파일을 업로드(`Upload`)하거나 `Save`를 진행한 후, 브라우저를 새로고침(`F5`)했을 때 파일 및 계산 데이터가 정상적으로 저장·유지되지 않고 초기화(날아감)되는 현상이 발생함.

### 원인 분석 및 기술적 한계
1. **브라우저 보안 샌드박스(File 객체 휘발성)**:
   - 웹 브라우저는 보안 정책상 로컬 디스크의 실제 파일(File/Blob 객체)을 새로고침 이후에도 `input[type="file"]` 슬롯에 영구 유지시키는 것을 허용하지 않습니다.
2. **GitHub Pages 정적 호스팅 배포 딜레이 (1~2분 지연)**:
   - 프론트엔드에서 `Save` 버튼을 눌러 GitHub API로 원격 저장소(`data/`)에 커밋을 올리더라도, GitHub Pages 서버가 새 커밋을 빌드하여 전 세계 CDN에 배포하기까지 **약 1~2분의 지연 시간**이 발생합니다.
   - 따라서 `Save` 직후 바로 새로고침을 누르면 GitHub Pages 서버가 아직 이전 상태(404 또는 구버전)를 응답하여 자동 불러오기가 실패합니다.
3. **로컬 캐시(localStorage/IndexedDB)와 서버 데이터 로드 간의 경합(Race Condition)**:
   - 로컬 캐시에서 데이터를 복원한 직후 백그라운드에서 `data/` 경로의 서버 파일을 다시 fetch하는 과정에서, 서버 파일이 불완전하거나 캐시 인코딩 문제가 발생할 경우 화면이 덮어씌워지거나 리셋되는 타이밍 이슈가 존재합니다.

### 향후 개선 및 해결 과제
- GitHub Pages의 빌드 딜레이와 무관하게 완전히 동작하도록 **GitHub Raw API 또는 Git API를 직접 조회하여 최신 커밋 데이터를 즉시 가져오는 방식** 검토.
- 새로고침 시 로컬 캐시가 존재하는 경우 서버 fetch 에러가 발생해도 로컬 화면을 절대 초기화하지 않도록 완벽한 락(Lock) 구조 적용.
- 정식 Admin 백엔드 API 개발 시 서버 데이터베이스에 영구 보관하는 방식으로 전환.
